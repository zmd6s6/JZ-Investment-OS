## Objective

Create the PostgreSQL persistence foundation needed by later stages without moving investment
authority into infrastructure code. Database writes and outbox writes must be atomic, auditable
records must remain append-only, governed mutable pointers must use optimistic concurrency, and job
retries must have exactly-once business effect through idempotency.

## Deliverables

- [x] Alembic configuration and an initial migration for the Master Spec core tables
- [x] Exact PostgreSQL `numeric`, UTC `timestamptz`, UUID, JSONB, foreign-key, uniqueness, and index

- [x] CI and local commands for PostgreSQL integration verification
- [x] Migration recovery/forward-fix documentation

## Acceptance criteria

1. `alembic upgrade head` succeeds against an empty PostgreSQL database and creates every required
   core table, constraint, and index; downgrade to base and re-upgrade are tested.
2. A failed Unit of Work leaves neither the business write nor its outbox/audit/event records.
3. A committed Unit of Work persists the business write and outbox record atomically.
4. Repeating a successful logical task with the same idempotency key does not repeat its business
   effect and returns the original completed TaskRun.
5. Concurrent execution of the same logical task is rejected by a transaction-scoped PostgreSQL
   advisory lock.
6. Stale writes to Position, Thesis current pointer, Decision state, and Policy current-version
   pointer fail with a coded optimistic-concurrency error.
7. Audit and event history cannot be updated or deleted through supported repositories or direct
   database writes.
8. Integration tests use synthetic data only and run against PostgreSQL 16.
9. Domain remains independent of SQLAlchemy, Alembic, FastAPI, worker, and adapter code.

## Scope completed

Revision `20260917_0001` creates all 35 core tables plus normalized Evidence-reference tables. It
enforces UUID keys, exact numerics, timezone-aware timestamps, core uniqueness and foreign keys,
append-only audit/event and immutable-artifact guards, and optimistic version columns. Focused ORM
repositories persist already-validated Policy, Position, Thesis, and Decision changes; business
state legality remains in the domain layer.

The reliable-job slice acquires a transaction-scoped advisory lock, validates timezone-aware
business time, rejects idempotency-key input drift, records attempts and sanitized failures, and
commits business, event, audit, and outbox writes in one Unit of Work. The Compose topology now runs
an Alembic one-shot before API and worker startup.

## Acceptance scenario slice

- S12 infrastructure slice: repeating a successful job with the same key reuses the completed
  TaskRun and does not repeat its business effect; lock contention, retry failure, input drift, and
  rollback paths are named integration tests.

Full Daily-job Evidence/Decision/report idempotency remains correctly scheduled for PR-08.

## Known limitations and rollback

Later stages still own the business repositories and workflows for the schema-only core tables.
There is no DSA ingestion, runtime Agent, approval API, execution path, or real Policy activation.
The only credentials in tests and Compose are explicitly marked local placeholders.

For an empty development database, downgrade to `base` and remove the PR-02 modules and dependency
together. For a populated database, stop writers, restore the verified backup into a separate
database if required, and ship a reviewed forward-fix; never rewrite the accepted migration or
delete audit history. Detailed steps are in `docs/runbooks/migrations.md`.
